# Моделирование трасс подключения к тепловым сетям

Прототип команды **«Контора»** для задачи № 2 ЛЦТ 2026.

Сервис принимает один GeoJSON территории, строит до трёх существенно разных вариантов подключения
перспективных точек к существующей тепловой сети, подбирает диаметры труб и рассчитывает стоимость
строительства. Каждый вариант независимо перепроверяется отдельным модулем. Найденные схемы
отображаются на карте по вкладкам и доступны для выгрузки в GeoJSON.

## Возможности

- Загрузка и проверка одного GeoJSON-файла (до 3 ГБ, потоковая обработка).
- Отображение зданий, существующей теплосети, точек подключения и ограничений на карте.
- Поиск допустимых трасс с учётом препятствий и необходимых отступов.
- Формирование общих участков сети для нескольких потребителей (совместное подключение).
- Подбор диаметров по суммарному расходу и допустимой длине.
- Расчёт стоимости трубопроводов, камер и врезок, штраф за неподключённые точки.
- До трёх основных вариантов, построенных строго по данным и правилам приложения.
- До трёх дополнительных вариантов с допущением (подход к ближайшей допустимой стороне здания —
  только для точек, которые по правилу подключить нельзя); допущения всегда перечислены на экране.
- Независимая проверка геометрии, топологии и расчётных параметров перед выдачей результата.
- Выгрузка выбранного результата в GeoJSON по разделу 7 технического приложения.
- Документация API (Swagger UI).

> В текущей версии расчёт использует только объекты загруженного файла. Автоматическая загрузка дорог
> OpenStreetMap и внешняя картографическая подложка для расчёта отключены. Если дороги и коммуникации
> отсутствуют в исходных данных, они не участвуют в расчёте.

## Сценарий использования

1. Откройте стартовую страницу.
2. Выберите или перетащите один файл `.geojson` либо `.json`.
3. Дождитесь проверки файла.
4. Расчёт начнётся автоматически и уйдёт в очередь на сервере; на экране видны прогресс и позиция в очереди.
5. Откроется страница результатов с картой и вкладками.
6. Во вкладке **«Исходные данные»** доступны карта и состав загруженного набора.
7. Во вкладках **«Решение 1–3»** отображаются основные варианты — построенные строго по данным и
   правилам приложения, с показателями и списком неподключённых точек с указанием причины.
8. Фильтром **«Дополнительные варианты»** включаются вкладки **«Доп. вариант 1–3»** — те же стратегии,
   но с допущением (подход к ближайшей допустимой стороне здания) только для точек, которые иначе
   подключить нельзя; допущения перечислены в панели варианта.
9. Выберите вариант и нажмите **«Выгрузить данные»**, чтобы скачать GeoJSON.

Слои карты можно включать и отключать в легенде. Нажатие на точку в списке приближает её на карте.

Если ни одного варианта без нарушений правил не найдено, показывается лучший из построенных с пометкой
о нарушении. Неподключённость конкретной точки означает, что подобранные стратегии не нашли для неё
допустимого пути, а не математическое доказательство невозможности подключения.

### Время расчёта

Первый расчёт файла занимает несколько минут: строятся графы видимости для поиска маршрутов. Повторный
расчёт того же файла быстрее — графы переиспользуются. Расчёт асинхронный и идёт на сервере фоновым
заданием; страницу можно не закрывать, прогресс обновляется периодическим опросом.

## Входные данные

Ожидается GeoJSON типа `FeatureCollection` с массивом `features`.

Координаты задаются в **WGS 84 / EPSG:4326**, порядок:

```text
[долгота, широта]
```

Для каждого объекта обязательны:

- корректная непустая `geometry`;
- `properties.id` — уникальный строковый или числовой идентификатор;
- `properties.object_type` — тип объекта.

Числовой идентификатор `1` и строковый `"1"` различаются.

### Основные типы объектов

| Объект | `object_type` | Требования |
|---|---|---|
| Источник теплоснабжения | `source` | Обычно `Point` |
| Существующий трубопровод | `heat_network` | `LineString`, поле `diameter` |
| Тепловая камера | `heat_chamber` | `Point` |
| Точка подключения здания | `oks_connection_point` | `Point`, положительный числовой `flow_tph` |
| Ограничение (включая здания) | `restriction` | Дополнительное поле `restriction_type`; полигоны зданий — `restriction_type: "oks"` |

`flow_tph` задаёт расход теплоносителя в тоннах в час. Он должен находиться непосредственно у точки
подключения. Расход, указанный только у связанного здания, его не заменяет.

Для поиска подключения необходим хотя бы один существующий трубопровод.

### Типы ограничений

Поддерживаемые значения `restriction_type` (таблица 2 приложения):

```text
oks              — существующий ОКС (в т.ч. здания), запрет, отступ 5 м
park             — парк, запрет, отступ 1 м
social_area      — территория социального объекта, запрет, отступ 1 м
prohibited_site  — запрещённая территория, запрет, отступ 1 м
water            — водный объект, запрет, отступ 1 м
railway          — железная дорога, запрет, отступ 1 м
road             — автомобильная дорога, специальный проход, угол ≥45°, K = 1,60
tram_tracks      — трамвайные пути, специальный проход, угол ≥45°, K = 1,75
gas_pipeline     — газопровод, специальное пересечение, отступ 2 м, K = 1,25
power_cable      — силовой кабель до 35 кВ, специальное пересечение, отступ 2 м, K = 1,15
heat_network     — пересечение чужой теплосети без врезки, отступ 1 м, K = 1,05
```

Для линейных дорог и трамвайных путей ширина в текущей версии не запрашивается у OpenStreetMap и не
подставляется произвольно — используется геометрия объекта из файла. Неподдерживаемые типы ограничений
не игнорируются молча — попадают в диагностику.

### Диаметры труб

Поддерживаемые значения `diameter`, мм:

```text
50, 65, 80, 100, 125, 150, 200, 250, 300,
400, 500, 600, 700, 800, 900, 1000, 1200, 1400
```

### Тестовые данные

В `test-data/` лежат файлы для проверки загрузки и диагностики (`valid.geojson` и примеры с ошибками
геометрии, дубликатами id, отсутствующим расходом и т. д.); ожидаемый результат проверки по каждому
файлу записан в `scripts/check-test-data.ps1`. Это проверка загрузки, а не готовый конкурсный набор.

## Алгоритм

### 1. Подготовка геометрии

Сервис читает GeoJSON, переводит координаты в метрическую систему EPSG:32637 (формулы Крюгера, без
внешней библиотеки) и строит пространственный индекс объектов.

### 2. Зоны отступов

Для каждого препятствия и диаметра трубы считается запретная зона: отступ по таблице приложения плюс
габарит объекта плюс половина ширины пары труб. Правила таблиц 1–2 приложения заданы как данные.

### 3. Поиск трассы

Строится граф видимости, маршрут ищется алгоритмом A* с учётом направления захода (поворот не более
90°) и особого прохода через дорогу или трамвайные пути одним атомарным участком.

### 4. Совместное подключение

Точки добавляются в общее дерево: к существующей сети или к уже построенной ветви другой точки. В узле
новой сети — не более четырёх примыкающих участков (проходящий ствол даёт два, своих ветвей — до двух).

### 5. Диаметры и стоимость

Расход участка — сумма расходов всех точек ниже по течению. Диаметр не убывает по направлению к сети;
у одного диаметра есть предельная длина непрерывного участка. Считаются стоимость труб, камер и врезок
и штраф за неподключённые точки.

### 6. Отбор вариантов

Несколько стратегий (разный порядок подключения точек и показатель оптимизации) строят сеть параллельно.
Варианты, различающиеся менее чем по 25% точек подключения (для каждой точки сравнивается, к какой
ветви или месту сети — с округлением до 10 м — она подключена), считаются одинаковыми: остаётся вариант
с лучшим показателем S. Из различающихся вариантов отбираются до трёх лучших.

### 7. Независимая проверка

Отдельный модуль, не использующий алгоритм поиска, заново проверяет топологию, отступы (прямым
расстоянием), расходы, диаметры, предельные длины и стоимость уже построенного варианта. Вариант с
нарушением правил не показывается, если есть правильный.

> Поиск эвристический: отсутствие найденного маршрута означает, что подобранные стратегии не нашли
> допустимого пути, а не доказанную невозможность подключения.

## Результат расчёта

Каждый вариант выгружается как часть одного GeoJSON `FeatureCollection` (раздел 7 приложения),
варианты различаются по `variant_id`.

В состав результата входят:

- новые участки теплосети (`heat_network`);
- новые камеры (`heat_chamber`);
- технические узлы (`technical_node`, там, где меняется способ прокладки без ветвления);
- сводка варианта (`variant_summary`).

Объект сводки имеет `geometry: null`.

Экспорт описывает рассчитанную сеть и не является полной копией исходного файла. Сохраняйте исходный
GeoJSON вместе с результатом: ссылки на существующие объекты используют их первоначальные идентификаторы.

### Показатели

| Поле | Описание |
|---|---|
| `construction_cost` | Стоимость строительства с учётом камер и врезок, ₽ |
| `chamber_construction_cost` | Стоимость камер, уже включённая в строительство, ₽ |
| `existing_chamber_tie_in_count` | Число врезок в существующие камеры |
| `existing_chamber_tie_in_cost` | Стоимость этих врезок, уже включённая в строительство, ₽ |
| `new_network_length` | Протяжённость новой сети, м |
| `unconnected_oks_ids` | Идентификаторы неподключённых точек |
| `unconnected_penalty` | Расчётный штраф за неподключённые точки, ₽ |
| `calculated_cost` | Стоимость строительства плюс расчётный штраф, ₽ |
| `score` | Значение показателя S |

Формула оценки:

```text
S = 0,7 × calculated_cost / 25 000 000
  + 0,3 × new_network_length / 100
```

Меньшее значение S предпочтительнее при сравнении вариантов.

**Важно:**

- расчётный штраф — компонент оценки, а не фактическая строительная работа;
- стоимость камер и врезок уже включена в `construction_cost`;
- длина и погонные расценки относятся к паре труб и не удваиваются;
- отсутствие нарушений у независимой проверки означает прохождение реализованных проверок, а не
  инженерную экспертизу.

## API

Базовый адрес при локальном запуске:

```text
http://localhost:8080
```

Документация: `http://localhost:8080/swagger-ui.html`.

| Метод | Адрес | Назначение |
|---|---|---|
| `POST` | `/api/upload` | Загрузка и проверка файла, сводка данных |
| `POST` | `/api/plan` | Постановка расчёта в очередь, ответ `202 {jobId, status}` |
| `GET` | `/api/plan/{jobId}` | Состояние задания и результат |
| `GET` | `/api/plan/{jobId}/export` | Выгрузка результата в GeoJSON |

### Загрузка файла

`POST /api/upload`, тип запроса `multipart/form-data`, поле формы `file` (ровно один файл).
Успешный ответ содержит статистическую сводку загруженных данных (число объектов по типам,
диагностику). При ошибке — `400` с текстом причины, например «Нет geometry у Feature #36».

### Постановка расчёта

`POST /api/plan`, тип запроса `multipart/form-data`. Поле `file` обязательно, поле `roads`
(дороги OpenStreetMap в формате GeoJSON) — необязательно; текущий интерфейс его не передаёт.

Ответ: `202 {"jobId": "...", "status": "QUEUED"}`.

### Состояние и результат

`GET /api/plan/{jobId}` — статус `QUEUED`, `RUNNING`, `DONE` или `FAILED`, прогресс в процентах,
позиция в очереди; при `DONE` в поле `result` — основные и дополнительные варианты и диагностика.

### Выгрузка

`GET /api/plan/{jobId}/export?additional=false` — GeoJSON по разделу 7 приложения; `additional=true`
добавляет дополнительные варианты (`a1`, `a2`, ...).

Одновременно выполняется один расчёт; остальные встают в очередь (до 50 заданий). При переполненной
очереди — `429`.

## Ограничения текущей версии

- Расчёт выполняется по загруженному набору данных. Дороги и коммуникации, отсутствующие в файле, не
  учитываются: автоматическая загрузка дорог OpenStreetMap для расчёта отключена.
- Используется фиксированная проекция EPSG:32637. Работа с другими географическими зонами требует
  настройки и проверки.
- Модель двумерная. Глубина прокладки не считается, в экспортируемых участках соответствующие поля
  оставлены `null`.
- Возможны частичные результаты и отсутствие найденной схемы для отдельных точек.
- Каталог диаметров, расценок и ограничений зафиксирован в коде по данным приложения.
- Поиск эвристический и ограничен по числу шагов; расчёт идёт по одному файлу за раз.
- Запуск через docker-compose проверен реальным CI-прогоном на Ubuntu; проверки на целевом сервере
  заказчика не было.

Прототип предназначен для предварительного моделирования. Полученные схемы требуют проверки
специалистами перед использованием в проектировании.

## Возможные проблемы

| Проблема | Решение |
|---|---|
| Команда `mvn` не найдена | Установите Maven и добавьте его в PATH либо используйте Maven в IDEA |
| Приложение не запускается | Проверьте JDK 11, загрузку зависимостей и журнал запуска |
| Порт 8080 занят | Остановите другой экземпляр или выберите другой порт |
| После обновления отображается старый интерфейс | Перезапустите приложение и обновите страницу через `Ctrl+F5` |
| Файл не проходит проверку | Проверьте структуру GeoJSON, идентификаторы, геометрию и обязательные поля |
| HTTP 429 при постановке расчёта | Дождитесь освобождения места в очереди |
| Решение не найдено для части точек | Причина показана в панели варианта и в выгрузке (`unconnected_oks_ids`) |
| Пробуете загрузить обратно файл экспорта | Экспорт — это результат (другая схема данных), а не входной файл; загружайте исходный GeoJSON |
